# OCR 캐시(문서 처리) 서비스 인터페이스 정의서

## 1. 개요

- **목적**: 문서(PDF/DOCX 등)를 Azure Document Intelligence로 OCR 처리하고, 그 결과(`document_hash` 기준)를 캐시하여 동일 내용의 문서가 재요청되면 재처리 없이 즉시 재사용한다.
- **처리 방식**: 하이브리드. 캐시에 완료된 결과가 있으면 **동기**로 즉시 반환(200)하고, 없으면 **비동기**로 접수(202)한 뒤 백그라운드에서 처리하며 완료/실패 시 콜백으로 결과를 전달한다.
- **캐시 키**: 파일 내용의 SHA-256 해시(`document_hash`) + 모델 ID + 출력 포맷 조합. **파일명이 달라도 내용이 같으면 같은 캐시를 공유**한다.
- **후속 연계**: 여기서 발급된 `document_hash`는 약관비교(약관검증) 서비스 요청 시 `ocrResltKey`로 사용된다.
- **Base URL**: `/api/v1/documents`

## 2. 공통 사항

### 2.1 공통 요청 필드

`POST /parse-di`는 `multipart/form-data`이며, 아래 필드가 공통으로 포함된다 (`ApiRequest` 상속).

| 필드명 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| userId | string | N | "" | 사용자 사번 |
| infId | string | N | "" | 인터페이스 ID (API별 고정값) |
| rqtKey | string | N | "" | 요청키 (클라이언트 생성 랜덤 키) |

### 2.2 공통 응답 봉투

모든 API 응답의 최상위 구조 (`ApiResponse`).

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| statusCode | int | Y | HTTP 상태코드 |
| statusMsg | string | Y | 상태 메시지 |
| result | object \| null | N | 결과 오브젝트. API/상황별로 내부 형식이 다르며 null일 수 있음 |

### 2.3 환경설정 (서버 측 고정값)

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| DOCUMENT_INTELLIGENCE_CALLBACK_URL | - | OCR 처리 완료/실패 시 결과를 전송할 콜백 URL. 클라이언트가 요청마다 지정하지 않고 서버에 고정 설정됨 |
| DOCUMENT_INTELLIGENCE_TIMEOUT_SECONDS | 300 | Document Intelligence 분석 대기 타임아웃(초) |
| MAX_UPLOAD_SIZE_MB | 20 | 업로드 허용 최대 파일 크기(MB) |

### 2.4 상태값 종합 정리

**(1) HTTP statusCode** — 모든 API 공통 응답 봉투(`statusCode`)에 실리는 값

| 값 | 의미 | 발생 API |
|---|---|---|
| 200 | 정상 처리 (캐시 히트 즉시 반환 포함) | POST parse-di, GET status |
| 202 | 요청 접수(비동기 처리 시작, 이미 처리중 포함) | POST parse-di |
| 400 | 요청 값 오류 (file/filePath 지정 방식 오류) | POST parse-di |
| 404 | 대상 리소스(document_hash) 없음 | GET status |
| 413 | 업로드 파일 크기 초과 | POST parse-di |
| 422 | 요청 Body(form) 형식/필수값 오류 | POST parse-di |
| 502 | 외부 연동(Storage 등) 처리 중 오류 | POST parse-di (드문 케이스, 4.1.2 참고) |
| 500 | 서버 내부 오류 | 모든 API (예외적) |

**(2) Job 내부 처리 상태** — `result.status` (POST parse-di 응답 및 GET status 응답 공통, 서버 내부 job 상태와 동일)

| 값 | 의미 |
|---|---|
| processing | 백그라운드에서 OCR 처리 진행 중 |
| completed | 처리 완료, 결과 파일 조회 가능 |
| failed | 처리 중 오류로 실패 종료 (다음 동일 문서 요청 시 자동으로 재처리됨) |

> `failed` 상태는 **GET status 조회**에서만 직접 관측된다. `POST parse-di`는 캐시가 `failed` 상태인 문서를 다시 요청받으면, 그 상태를 그대로 응답하지 않고 즉시 재처리를 시작(202 신규 접수와 동일하게 응답)한다.

> **주의**: 실제 OCR 처리(Document Intelligence 호출) 자체의 성공/실패는 이 API의 응답이 아니라 **콜백**(4.3절) 또는 **GET status 조회**(4.2절)로만 알 수 있다. 이 API의 200/202는 캐시 히트 또는 "요청을 접수했는가"에 대한 응답이며, 위 표의 400/413/422/502/500만 요청 자체의 실패다.

#### 처리 로직 요약

1. 업로드된 파일 내용의 SHA-256 해시(`document_hash`)와 모델 ID/출력 포맷으로 캐시 키를 구성한다. **같은 내용이면 파일명이 달라도 동일 캐시를 공유**한다.
2. 캐시가 `completed`면 즉시 그 결과를 반환한다(재처리 없음, hit_count 증가).
3. 캐시가 `processing`이고 마지막 갱신 시각이 20분 이내(`STALE_PROCESSING_THRESHOLD`)면 재처리 없이 "처리 중" 응답만 반환한다.
4. 캐시가 없거나, `failed`이거나, `processing`인데 20분 넘게 갱신이 없으면(정체된 처리로 간주) 새로 처리를 시작한다.
5. 신규 처리는 원본 파일을 Storage에 저장(`file` 업로드 시) → Document Intelligence 분석 → 결과(markdown/JSON)를 Storage에 저장 → 캐시 상태를 `completed`로 갱신하는 순서로 진행되며, 그중 하나라도 실패하면 캐시 상태가 `failed`로 기록되고 실패 콜백이 전송된다.

## 4.3 콜백 명세

### 4.3.1 콜백 발신 (본 서버 → 클라이언트)

- **URL**: 서버 환경설정(`DOCUMENT_INTELLIGENCE_CALLBACK_URL`)에 고정. 요청마다 클라이언트가 지정하지 않음
- **Method**: POST
- **Content-Type**: application/json
- **발신 시점**: `parse-di` 요청으로 신규(또는 재) 처리가 시작되어, 그 백그라운드 처리가 완료/실패로 종료됐을 때. **캐시 히트(200)나 "이미 처리 중"(202) 응답인 경우엔 이번 요청으로 인한 콜백이 발생하지 않는다** (해당 처리를 시작한 최초 요청 시점에 이미 콜백이 발신됐거나 발신될 예정).

#### Callback Body

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| termId | string | Y | 원 요청의 값 그대로 |
| termHstSeq | string | Y | 원 요청의 값 그대로 |
| fileDivCd | string | Y | 원 요청의 값 그대로 |
| ocrResltKey | string \| null | N | 성공 시 `document_hash`. **실패 시 null** |
| ocrErrSbst | string \| null | N | 실패 시 오류 내용. **성공 시 null** |

> 이 콜백에는 `statusCode`/`statusMsg`/`userId`/`infId`/`rqtKey` 필드가 없다. 성공/실패 여부는 `ocrResltKey`와 `ocrErrSbst` 중 어느 쪽에 값이 채워졌는지로 판단한다.

**성공 예시**
```json
{
  "termId": "T12345",
  "termHstSeq": "1",
  "fileDivCd": "01",
  "ocrResltKey": "a3f5c9d8e1b2...",
  "ocrErrSbst": null
}
```

**실패 예시**
```json
{
  "termId": "T12345",
  "termHstSeq": "1",
  "fileDivCd": "01",
  "ocrResltKey": null,
  "ocrErrSbst": "Document Intelligence 호출 중 오류가 발생했습니다: ..."
}
```

### 4.3.2 콜백 응답 (클라이언트 → 본 서버)

클라이언트의 콜백 수신 엔드포인트는 아래 형식으로 응답해야 한다. **HTTP 상태코드가 200이어도 `result` 값으로 실제 처리 성공 여부를 판단한다.**

| 필드명 | 타입 | 필수 | 설명 |
|---|---|---|---|
| result | int | Y | 0 = 성공, 0이 아니면(예: 1) 실패 |
| message | string | N | 실패 사유 등 메시지 |
| data | any | N | 사용 안 함 |

**정상 처리 (result=0)**
```json
{ "result": 0, "message": "OK", "data": null }
```

**클라이언트 측 처리 실패 (result≠0)**
```json
{ "result": 1, "message": "약관 ID를 찾을 수 없음", "data": null }
```

### 4.3.3 콜백 재시도 정책

| 실패 유형 | 재시도 여부 | 비고 |
|---|---|---|
| HTTP 레벨 에러 (타임아웃, 5xx 등) | O | 1초 → 2초 → 4초 backoff로 최대 3회 시도 |
| HTTP 200 + `result != 0` (비즈니스 레벨 실패) | X | 전달 자체는 성공했으므로 재시도하지 않고 실패로 기록만 함 |
| 응답 본문이 JSON이 아님 | X | 실패로 기록만 함 |

> 이 서비스에는 약관검증 서비스의 `resend-callback`과 같은 콜백 재전송 API가 없다. 콜백 전달 자체가 실패한 경우, 클라이언트는 GET status 조회로 결과를 확인해야 한다.

## 5. 부록: 참고 사항

- 캐시 키는 파일 내용의 SHA-256 해시 기준이므로, **파일명이 달라도 내용이 동일하면 같은 캐시를 공유**하고 재처리하지 않는다.
- 처리가 `processing` 상태로 20분(`STALE_PROCESSING_THRESHOLD`) 넘게 갱신되지 않으면 정체된 처리로 간주하여, 다음 동일 문서 요청 시 자동으로 재처리를 시작한다.
- `failed` 상태의 캐시도 영구 실패가 아니며, 다음 동일 문서 요청이 오면 자동으로 재처리를 시도한다(별도 초기화 API 불필요).
- `file` 업로드 시 원본은 Storage에 저장되고(`existing_file_path`가 없을 때만), `filePath`로 지정한 경우 기존 파일을 그대로 재사용하며 별도로 복사하지 않는다.
- Job/결과 데이터의 보관 기간(retention) 정책은 별도로 두지 않는다(무기한 보관).
- 결과 파일(`result_file_path`/`result_json_path`)은 클라이언트가 직접 다운로드하는 용도가 아니라, 후속 서비스(예: 약관검증)가 `document_hash`(`ocrResltKey`)로 내부 조회할 때 사용하는 경로다.
