# 약관비교(약관검증) 서비스 인터페이스 정의서

## 1. 개요

- **목적**: 상품별 항목 데이터(itemNm/value)를 실제 약관 원문(OCR 처리된 문서)과 대조하여 일치 여부를 검증하고, 값이 없는 항목은 약관에서 추출한다.
- **처리 방식**: 비동기. 요청은 즉시 접수(202)되고, 실제 처리는 백그라운드에서 진행되며 완료/실패 시 콜백으로 결과를 전달한다.
- **선행 조건**: 검증에 사용할 약관 문서는 미리 `POST /api/v1/documents/parse-di`로 OCR 처리가 완료되어 있어야 하며, 그때 발급된 `document_hash`를 본 서비스의 `ocrResltKey`로 사용한다.
- **Base URL**: `/api/v1/terms`

## 2. 공통 사항

### 2.1 공통 요청 필드

모든 요청 Body에 공통으로 포함되는 필드 (`ApiRequest` 상속).

| 필드명 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| userId | string | N | "" | 사용자 사번 |
| infId | string | N | "" | 인터페이스 ID (API별 고정값) |
| rqtKey | string | N | "" | 요청키 (클라이언트 생성 랜덤 키). Job의 고유 식별자로 사용됨 |

### 2.2 공통 응답 봉투

모든 API 응답의 최상위 구조 (`ApiResponse`).

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| statusCode | int | Y | HTTP 상태코드 |
| statusMsg | string | Y | 상태 메시지 |
| result | object \| null | N | 결과 오브젝트. API/상황별로 내부 형식이 다르며 null일 수 있음 |

### 2.3 환경설정 (서버 측 고정값)

| 환경변수 | 설명 |
|---|---|
| TERMS_VERIFICATION_CALLBACK_URL | 처리 완료/실패 시 결과를 전송할 콜백 URL. 클라이언트가 요청마다 지정하지 않고 서버에 고정 설정됨 |
| TERMS_VERIFICATION_CONCURRENCY | 내부 LLM 호출 동시성 제한 (기본 5) |

### 2.4 상태값 종합 정리

본 인터페이스에는 성격이 다른 4종류의 "상태값"이 있다. 혼동하지 않도록 한 곳에 정리한다.

**(1) HTTP statusCode** — 모든 API 공통 응답 봉투(`statusCode`)에 실리는 값

| 값 | 의미 | 발생 API |
|---|---|---|
| 200 | 정상 처리 | GET 조회, resend-callback |
| 202 | 요청 접수(비동기 처리 시작, 이미 처리중/완료 포함) | POST verify |
| 400 | 요청은 유효하나 현재 상태상 처리 불가 | resend-callback (미완료 job) |
| 404 | 대상 리소스(rqtKey) 없음 | GET 조회, resend-callback |
| 422 | 요청 Body 형식/필수값 오류 | POST verify |
| 500 | 서버 내부 오류 | 모든 API (예외적) |

**(2) Job 내부 처리 상태** — GET 조회 API의 `result.status`에 나타나는 값 (서버 내부 job 상태와 동일)

| 값 | 의미 |
|---|---|
| processing | 백그라운드에서 처리 진행 중 |
| completed | 처리 완료, 콜백 전송(또는 재전송) 완료/시도됨 |
| failed | 처리 중 오류로 실패 종료 |

**(3) 항목 판정 상태** — 콜백/조회 결과의 `data[].documents[].items[].status`

| 값 | 의미 | 발생 조건 |
|---|---|---|
| MATCHED | 검증 통과 | value가 있고 약관 내용과 일치 |
| MISMATCH | 검증 불일치 | value가 있는데 약관 내용과 다름 (llmValue에 정정값) |
| EXTRACTED | 값 추출됨 | value가 없고 약관에서 값을 찾음 |
| NOT_FOUND | 내용 없음 | 약관에 해당 항목 내용 자체가 없음 (value 유무 무관) |

**(4) 콜백 처리 결과 코드** — 클라이언트가 콜백 응답으로 돌려주는 `result` (4.4.2절 참고)

| 값 | 의미 |
|---|---|
| 0 | 클라이언트가 콜백을 정상 처리함 (성공) |
| 0 이외(예: 1) | 클라이언트가 콜백 처리에 실패함 |

| No | Method | Path | 설명 |

## 4. API 상세

### 4.1 `POST /api/v1/terms/verify` — 약관 검증 요청 접수

#### Request Body

| 필드명 | 타입 | 필수 | 설명 |
|---|---|---|---|
| userId, infId, rqtKey | string | N | 공통 요청 필드 (2.1 참고) |
| documentHash | array | Y (1개 이상) | 검증에 쓰일 약관 문서 풀 |
| documentHash[].ocrResltKey | string | Y | OCR 캐시 조회 키 (parse-di 결과의 document_hash) |
| documentHash[].termNm | string | Y | 표시용 약관명 (처리 로직에는 사용되지 않고 결과에 그대로 echo됨) |
| data | array | Y (1개 이상) | 검증 대상 상품 목록. 각 상품의 items는 documentHash의 **모든** 문서와 교차 비교됨 |
| data[].name | string | Y | 상품명 |
| data[].items | array | Y (1개 이상) | 검증/추출 대상 항목 목록 |
| data[].items[].itemNm | string | Y | 항목명 |
| data[].items[].value | string \| null | N | 검증할 값. 없거나 빈 문자열/공백이면 null로 취급되어 "추출" 모드로 동작 |
| data[].items[].desc | string \| null | N | itemNm에 대한 설명 (빈 문자열/공백은 null로 취급) |
| knwlgInfoId | integer | Y | 지식 정보 ID. 콜백 본문에 받은 값 그대로 실려감 |
| termVrfSeq | integer | Y | 약관 버전 순번. 콜백 본문에 받은 값 그대로 실려감 |

**Request 예시**

```json
{
  "userId": "12345",
  "infId": "TERMS_VERIFY_V1",
  "rqtKey": "k3n9X2b7QsT1m8pZ",
  "documentHash": [
    { "ocrResltKey": "a3f5c9d8e1b2...", "termNm": "KT 요고 시리즈 이용약관" },
    { "ocrResltKey": "b7e2f4a1c9d3...", "termNm": "KT 베이직 요금제 약관" }
  ],
  "data": [
    {
      "name": "요고 69",
      "items": [
        { "itemNm": "초이스 상품여부", "value": "Y", "desc": "선택형 상품 여부" },
        { "itemNm": "이용 가능 고객", "value": "개인, 미성년자, 외국인", "desc": "가입 가능 대상" }
      ]
    }
  ],
  "knwlgInfoId": 123456789012,
  "termVrfSeq": 3
}
```

#### 응답 필드 (공통, 202/422 동일 구조)

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| statusCode | int | Y | 202 또는 422 (4.1.1/4.1.2 참고) |
| statusMsg | string | Y | 상태 메시지 |
| result | null | Y (값은 항상 null) | 실제 결과는 콜백으로 전달되므로 이 응답에는 담기지 않음 |

#### 4.1.1 정상 응답 케이스 (모두 HTTP 202)

요청 형식이 유효하면 **항상 202**를 반환한다. 실제 검증 성공/실패 여부는 이 응답에 담기지 않고, 나중에 콜백으로 전달된다. 아래 3가지는 접수 상황에 따른 `statusMsg` 차이다.

| 상황 | statusMsg | 후속 동작 |
|---|---|---|
| 신규 요청 접수 | "약관 검증 요청을 접수했습니다." | 백그라운드에서 신규 처리 시작 |
| 같은 rqtKey가 이미 처리 중(2시간 이내) | "이미 처리 중입니다." | 재처리하지 않음. 기존 처리가 끝나면 콜백이 감 |
| 같은 rqtKey가 이미 완료됨 | "이미 완료된 요청입니다. 저장된 결과를 다시 전송합니다." | 재검증 없이 저장된 결과를 콜백으로 재전송 |

**예시**
```json
{ "statusCode": 202, "statusMsg": "약관 검증 요청을 접수했습니다.", "result": null }
```

#### 4.1.2 실패 응답 케이스

| HTTP Code | 상황 | statusMsg | 비고 |
|---|---|---|---|
| 422 | Request Body가 스키마에 안 맞음 (필수값 누락, 타입 불일치, 빈 배열 등) | "요청 값이 올바르지 않습니다." | 이 경우엔 접수 자체가 안 되므로 콜백도 전송되지 않음 |
| 500 | 서버 내부 오류 (예외 상황) | 서버 내부 오류 메시지 | 드문 케이스 |

**예시**
```json
{ "statusCode": 422, "statusMsg": "요청 값이 올바르지 않습니다.", "result": null }
```

> **주의**: 검증 처리 자체(약관 대조 결과)의 성공/실패는 이 API의 응답이 아니라 **콜백**으로만 알 수 있다 (4.4절 참고). 이 API의 202/422/500은 "요청을 접수했는가"에 대한 응답일 뿐이다.

#### 처리 로직 요약

1. `documentHash`는 `ocrResltKey` 기준으로 중복 제거된다 (같은 문서가 두 번 와도 로드/호출은 한 번만).
2. 각 item의 `value`가 여러 조건을 담고 있으면(예: 줄바꿈 포함 긴 텍스트) 독립적으로 검증 가능한 단위로 자동 분해된다. 분해는 `documentHash` 문서 수와 무관하게 item당 한 번만 수행된다.
3. 분해된 각 조건(claim)은 `documentHash` 풀의 **모든** 문서와 교차 비교된다 — 즉 최종 LLM 호출 수는 `상품 수 × 문서 수 × (분해된 조건 수 합)`이다.
4. 관련 없는 name-문서 조합은 대부분 `NOT_FOUND`로 채워지며, 이는 cross-product 설계상 의도된 결과다.
5. 항목(또는 문서 로드) 하나라도 처리에 실패하면 **전체 요청이 실패로 처리**되고, 진행 중이던 나머지 호출은 취소된 뒤 실패 콜백이 전송된다. 부분 성공 결과는 존재하지 않는다.

### 4.2 `GET /api/v1/terms/verify/{rqtKey}` — 처리 상태/결과 조회

#### Path Parameter

| 이름 | 타입 | 필수 | 설명 |
|---|---|---|---|
| rqtKey | string | Y | 조회할 요청의 rqtKey |

#### 4.2.1 정상 응답 케이스 (HTTP 200)

`result`의 형식은 Job 내부 처리 상태(2.4절 (2))에 따라 3가지로 나뉜다.

**① status=processing**

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| status | string | Y | "processing" |
| errorMessage | null | Y (값은 항상 null) | 처리 중이므로 오류 없음 |

```json
{ "statusCode": 200, "statusMsg": "OK", "result": { "status": "processing", "errorMessage": null } }
```

**② status=failed**

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| status | string | Y | "failed" |
| errorMessage | string | Y | 실패 사유 |

```json
{ "statusCode": 200, "statusMsg": "OK", "result": { "status": "failed", "errorMessage": "문서가 아직 처리 중입니다: a3f5c9d8e1b2..." } }
```

**③ status=completed** — `result`가 콜백 본문의 `data`/`usage`와 동일한 형식 (4.4.1절 참고)

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| data | array | Y | 검증 결과 (4.4.1절 데이터 구조와 동일) |
| usage | object | Y | 처리 통계 (4.4.1절 참고) |

#### 4.2.2 실패 응답 케이스

| HTTP Code | 상황 | statusMsg |
|---|---|---|
| 404 | 존재하지 않는 rqtKey | "해당 문서를 찾을 수 없습니다." |

```json
{ "statusCode": 404, "statusMsg": "해당 문서를 찾을 수 없습니다.", "result": null }
```

### 4.3 `POST /api/v1/terms/verify/{rqtKey}/resend-callback` — 콜백 재전송

완료된 job의 저장된 결과를 **재검증 없이** 그대로 다시 콜백으로 전송한다. 콜백 전송 자체가 실패했을 때 복구 용도로 사용한다.

#### Path Parameter

| 이름 | 타입 | 필수 | 설명 |
|---|---|---|---|
| rqtKey | string | Y | 재전송할 요청의 rqtKey |

#### 4.3.1 정상 응답 케이스 (HTTP 200)

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| statusCode | int | Y | 200 |
| statusMsg | string | Y | "재전송을 시작했습니다." |
| result | null | Y (값은 항상 null) | - |

```json
{ "statusCode": 200, "statusMsg": "재전송을 시작했습니다.", "result": null }
```

재전송은 백그라운드로 처리되므로, 이 응답은 "재전송을 시작했다"는 뜻이며 실제 콜백 전달 성공 여부는 이 응답에 담기지 않는다.

#### 4.3.2 실패 응답 케이스

| HTTP Code | 상황 | statusMsg |
|---|---|---|
| 404 | 존재하지 않는 rqtKey | "해당 문서를 찾을 수 없습니다." |
| 400 | job이 아직 완료되지 않음(processing/failed 상태) | "완료된 job만 재전송할 수 있습니다." |

```json
{ "statusCode": 400, "statusMsg": "완료된 job만 재전송할 수 있습니다.", "result": null }
```

## 4.4 콜백 명세

### 4.4.1 콜백 발신 (본 서버 → 클라이언트)

- **URL**: 서버 환경설정(`TERMS_VERIFICATION_CALLBACK_URL`)에 고정. 요청마다 클라이언트가 지정하지 않음
- **Method**: POST
- **Content-Type**: application/json
- **발신 시점**: `verify` 요청 처리 완료 시(성공/실패 모두), 또는 `resend-callback` 호출 시

#### Callback Body (공통 필드)

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| userId, infId, rqtKey | string | Y | 원 요청의 값 |
| knwlgInfoId | integer | Y | 원 요청의 값 그대로 |
| termVrfSeq | integer | Y | 원 요청의 값 그대로 |
| statusCode | int | Y | 200(성공) 또는 500(처리 중 오류) |
| statusMsg | string | Y | 성공 시 "OK", 실패 시 오류 메시지 |
| data | array \| null | N | 검증 결과. **성공 시에만 값 존재, 실패 시 null** |
| usage | object \| null | N | 처리 통계. **성공 시에만 값 존재, 실패 시 null** |

#### 성공 케이스 (statusCode=200)

`data`/`usage`에 실제 검증 결과가 채워진다. 아래는 각 데이터 구조의 상세다.

**data[] 구조** (`TermsNameResult`)

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| name | string | Y | 상품명 (요청의 data[].name) |
| documents | array | Y | 이 상품을 검증한 각 문서별 결과 |

**data[].documents[] 구조** (`TermsDocumentItemsResult`)

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| ocrResltKey | string | Y | 문서 식별 키 (요청의 documentHash[].ocrResltKey) |
| termNm | string | Y | 약관명 (요청의 documentHash[].termNm) |
| items | array | Y | 이 문서에 대한 항목별 검증 결과 |

**data[].documents[].items[] 구조** (`TermsItemResult`)

| 필드명 | 타입 | 필수(Not Null) | 설명 |
|---|---|---|---|
| itemNm | string | Y | 항목명 |
| value | string \| null | N | 원본 요청 값. 요청에 value가 없었으면 null |
| subClaim | string \| null | N | value가 여러 조건으로 분해된 경우 그중 하나의 조건. **분해 안 됐으면 null** |
| status | string (enum) | Y | 판정 결과 4종 중 하나 (2.4절 (3) 참고) |

### 4.4.2 콜백 응답 (클라이언트 → 본 서버)

클라이언트의 콜백 수신 엔드포인트는 아래 형식으로 응답해야 한다. **HTTP 상태코드가 200이어도 `result` 값으로 실제 처리 성공 여부를 판단한다.**

| 필드명 | 타입 | 필수 | 설명 |
|---|---|---|---|
| result | int | Y | 0 = 성공, 0이 아니면(예: 1) 실패 |
| message | string | N | 실패 사유 등 메시지 |
| data | any | N | 사용 안 함 |

**정상 처리 (result=0)**
```json
{ "result": 0, "message": "OK", "data": null }
```

**클라이언트 측 처리 실패 (result≠0)**
```json
{ "result": 1, "message": "지식 정보 ID를 찾을 수 없음", "data": null }
```

### 4.4.3 콜백 재시도 정책

| 실패 유형 | 재시도 여부 | 비고 |
|---|---|---|
| HTTP 레벨 에러 (타임아웃, 5xx 등) | O | 1초 → 2초 → 4초 backoff로 최대 3회 시도 |
| HTTP 200 + `result != 0` (비즈니스 레벨 실패) | X | 전달 자체는 성공했으므로 재시도하지 않고 실패로 기록만 함 |
| 응답 본문이 JSON이 아님 | X | 실패로 기록만 함 |

## 5. 부록: 참고 사항

- `documentHash[].ocrResltKey`에 대응하는 문서는 반드시 사전에 `POST /api/v1/documents/parse-di`로 OCR 처리가 완료(`status=completed`)되어 있어야 하며, 처리 중이거나 존재하지 않으면 해당 요청은 전체 실패로 처리된다.
- `evidence`/`page`는 LLM이 보고하는 값으로, 자동으로 원문과 대조 검증되지 않는다 (참고용).
- 요청 크기(상품 수 × 문서 수 × 항목 수) 상한은 두지 않는다.
- Job/결과 데이터의 보관 기간(retention) 정책은 별도로 두지 않는다(무기한 보관).
